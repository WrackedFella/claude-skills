# D0045 Card PRs keep their own review; feature-branch batching is not adopted as the default

- **Status:** Proposed, 2026-11-27.
- **Decision:** Cards keep merging into `dev` one by one, each with its own PR review (D0029). A feature integration branch stays the exception CLAUDE.md already describes (cards that cannot land alone), not a way to defer review. Deferring card reviews to one feature-level review is tested first (D0046) and adopted only if it passes the bar there.
- **Why:**
  - **The saving is real but capped.** Orchestrate (intake, builder, orchestrator loop, step-11 reviewer, wiki) is 68% of recorded spend and runs per card whatever the PR target. Only the PR review and fix rounds (32%) can move. Per-card review plus fix averages about $1.6 an issue ($78 over 49 issues); one review of N cards' diff costs about what two card reviews cost (per-issue cost is $3.88 under 500 lines, $5.83 at 500-1000, $6.29 above, so about 1.6x for 2x the lines), so the saving is about (N-2)/N of 32%: 0 at N=2, 13% at N=3, 19% at N=5, and only if review quality holds. Fix rounds on a larger diff, a second round that costs as much as the first (D0037) and a human sign-off would eat part of it.
  - **Review quality falls as the diff grows.** Vendor-reported inspection data puts defect detection per line falling past 200-400 lines (S47). devflow's own limit says the same: sign-off is `human` above 400 non-test lines, or 3000 for a light-tier PR with green gate and mutation (#128). A five-card feature is 1500-3000 lines, so most feature PRs would route to a person, which is the review D0029 declined to create; a chain branch "moves the human review, it doesn't remove it".
  - **Per-card review catches card-local defects while they are cheap to fix.** 46 of 102 recent merged moho PRs had a bot review (2026-11-27 sample); 12 needed 2+ reviews. The review of #1081 blocked a hip-band calculation that would have broken the feature's next cards (#982, #983); caught in the card, the fix was one function and one test. In a chain, later cards are built on top of earlier ones, so an unreviewed defect is read and extended by the next builder. Whether late defects cost more is contested for human teams (S48 finds no consistent increase in resolve time); for agents building on top of it, this is a hypothesis, not a measurement.
  - **The workflow assumes `dev`.** Verified in moho: `merge-eligibility.sh` refuses any base but `dev`; `conflicts.yml` scans `base=dev` only; `chain.yml` starts cards on the default branch and advances on issue close, and `Closes #N` closes nothing on a non-default base (S28), so a chain would stall; the `feature/**` ruleset blocks `ci-fix` pushes to the head. Each is a change, with its own risk, to save at most 13-19% of spend.
  - **Frequency of integration matters more than batch size.** Trunk-based guidance and a 565-repository study tie delivery speed to merge frequency, not merge size (S49). Cards into `dev` keep `dev` current for parallel work and keep conflicts small (D0031).
- **Cheaper levers first (D0035-D0037):** round 2+ reads the delta; run-record yield data shows what the step-11 reviewer and PR review leave behind, which is what decides whether the two overlap (D0038).
- **Sources:** S47, S48, S49, S28.
- **Reopen when:** D0046 shows a feature-level review matches the per-card reviews' blockers at lower cost, or `PR_AUTOMERGE=all` makes sign-off independent of size.
